# Google Classroom integration design

Status: **feasible, not implemented**. Official Google documentation checked October 7, 2026. No Google project, OAuth registration, school account, Marketplace listing or live Classroom connection has been configured or tested. This design does not establish production readiness.

## Delivery approach

Start with the **Classroom API and Google Drive**, then consider an embedded **Classroom Add-on**. The API can create coursework, attach material, retrieve authorized submissions, and support submission/grade actions. A Drive attachment's `STUDENT_COPY` sharing mode requests a separate copy for each student. Coursework creation requires a teacher of that course; an administrator who is not its teacher does not acquire that permission merely by being an administrator. [Coursework guide](https://developers.google.com/workspace/classroom/guides/manage-coursework), [Drive material sharing](https://developers.google.com/workspace/classroom/reference/rest/v1/Material).

The first coherent workflow would let an authorized teacher select a PDF in Drive, create a Margin-linked assignment, and let verified students open their own work in Margin. Reuse the document editor, encrypted persistence and ordered operation model behind a new provider-specific authorization boundary. Do not present local assignment states or saved annotations as a Classroom submission.

Submission writes have important project restrictions. `turnIn`, `reclaim` and attachment modification require the OAuth developer project that created the coursework or a corresponding add-on attachment. Only the owning student may turn in or reclaim; turning in transfers attached Drive file ownership to the teacher, and reclaiming returns it. Do not promise write access to arbitrary pre-existing Classroom assignments. [Turn in](https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork.studentSubmissions/turnIn), [reclaim](https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork.studentSubmissions/reclaim), [attachments](https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork.studentSubmissions/modifyAttachments).

Teachers may patch draft and assigned grades for eligible coursework; the add-on alternative requires Grade Sync enabled. Returning work is a separate operation and does not copy the draft grade into the assigned grade automatically. Submission, grading and return need explicit actions, confirmed provider results and recovery for uncertain outcomes. [Grade patch](https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork.studentSubmissions/patch), [return](https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork.studentSubmissions/return).

## Identity and authorization boundary

Current [LMS contracts](../packages/lms/src/types.ts) expose a Canvas-only LTI launch provider. The [student-work runtime](../apps/api/src/assignments/work/pool.ts) requires an LTI student session, and `/canvas/work` relies on that verified launch. Google Classroom is not another issuer to insert into those Canvas contracts. Its provider adapter, routes, server grants and tests must be designed explicitly before sharing runtime paths.

Google sign-in authenticates an account; **it does not grant Classroom or Drive authorization**. Validate identity tokens and OAuth state/PKCE using registered clients and trusted issuer/key configuration. Bind the verified issuer/subject to the correct Margin organization and a server-registered Google integration. Treat email, claimed domain, role preferences and browser-supplied course/file IDs as hints, never authority.

Before releasing source bytes or accepting an operation, resolve and verify the course, coursework, authenticated course membership/teacher authority, student submission owner, source file and current provider access. Pin their server-verified relationship to the local work binding and document revision. Recheck account, permission and resource changes at appropriate online boundaries; an old local snapshot is provenance, not perpetual access. Never adopt an unrelated local PDF into a Classroom assignment automatically.

Keep Google access/refresh credentials out of the local document vault and browser logs. The proposed server token store must encrypt credentials, limit their lifetime/access, handle rotation and revocation, and separate account login from feature-specific consent. Logout, tenant/account replacement and revoked school access must cancel current work requests and prevent new dispatch without discarding already encrypted drafts. Exact retry and submission-state reconciliation need provider-specific contracts; do not assume Google mutation APIs accept Margin operation IDs as idempotency keys.

## Consent, school controls and Add-ons

A Google Cloud project and enabled APIs are required; basic Classroom development does not require paid Cloud features. Request only scopes for implemented features, with incremental consent where possible. Candidate scopes include `classroom.courses.readonly`, teacher `classroom.coursework.students`, student `classroom.coursework.me`, and roster access only if required. Public applications requesting sensitive or restricted scopes must satisfy Google's applicable verification requirements. [Prerequisites](https://developers.google.com/workspace/classroom/guides/onboarding/prerequisites), [Classroom authorization](https://developers.google.com/workspace/classroom/guides/auth).

Prefer Google Picker with `drive.file` for selected/app-created files instead of blanket Drive access. Classroom metadata permission does not itself permit downloading the attached Drive file, and `drive.file` does not automatically expose every student's copy. Verify actual teacher/student file access in the sandbox before committing to the import workflow. [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [coursework permissions](https://developers.google.com/workspace/classroom/guides/manage-coursework).

School administrators control third-party app access, especially for accounts designated under 18. Plan for blocked/unapproved apps, consent refusal and revoked permissions. Publish accurate data-use/privacy disclosures and apply Google's minimum-access, secure-handling and applicable Limited Use requirements. School/student privacy review is a delivery gate, not a property conferred by OAuth verification. [School administration](https://developers.google.com/workspace/classroom/guides/key-concepts/admin-actions), [Google user-data policy](https://developers.google.com/terms/api-services-user-data-policy).

An Add-on embeds teacher/student/grading experiences inside Classroom and distributes through Google Workspace Marketplace. Teachers need Education Teaching & Learning or Education Plus licenses, and administrators control installation/allowlisting. Public release requires OAuth verification and Marketplace review, plus eligible test users and configured hosted endpoints. Add-on scopes and iframe authentication need a separate least-privilege design. This license requirement applies to the Add-on route, not every core Classroom API use. [Add-ons overview](https://developers.google.com/workspace/classroom/add-ons), [administrator requirements](https://support.google.com/edu/classroom/answer/12351654?hl=en), [publication process](https://developers.google.com/workspace/classroom/add-ons/get-started/get-started-overview).

## Document and export policy

Margin's current `.margin` export is an encrypted package, not a PDF that Drive/Classroom can preview directly. The proposed first integration should attach an authenticated Margin link and retain encrypted local/server storage. The link identifies work but grants no access by itself; teacher/student authorization remains mandatory on open.

Uploading an ordinary rendered PDF to Drive would expose a decrypted document to the authorized Google storage workflow. That is a separate, explicit product/security decision under the original encryption requirements, with user intent, school policy, ownership/retention and sharing controls defined first. Do not silently convert encrypted exports into ordinary Drive PDFs, treat a shared link as private, or infer export permission from successful import. A Classroom-managed Drive copy and a Margin-managed private work copy must have an explicit relationship rather than being described as the same storage object.

## Required real sandbox acceptance tests

These are planned acceptance tests, **not completed evidence**. Use a registered test project, a school test domain where needed, a teacher, two students and a separate course/organization; use synthetic documents only.

1. Verify login and incremental consent independently; exercise denied scopes, wrong account/domain, blocked under-18 access, refresh expiry, revocation and cross-organization attempts. Confirm credentials/content are absent from logs and browser persistence.
2. Create coursework as the actual teacher; reject a non-teacher administrator and unrelated student. Confirm provider/project association and clear refusal for unsupported mutations of foreign-project coursework.
3. Exercise `STUDENT_COPY`, verify distinct Drive IDs/ownership/access for both students, and confirm explicit file selection/access is sufficient. Test inaccessible/deleted files and removed course membership without releasing another student's bytes.
4. Open the correct PDF in Margin; reject forged course/coursework/submission/file IDs and mismatched source versions. Verify encrypted local save, reload/unlock, offline edits after verified open, exact retry, conflict retention and account switching without cross-student draft adoption.
5. Turn in as the owning student, check actual provider state and Drive ownership, then reclaim and teacher-return. Simulate a lost response after a successful mutation and reconcile state without falsely claiming success or rollback. Keep annotation save distinct from submission.
6. Set draft/assigned grades and return work as an authorized teacher; verify project/Grade Sync restrictions, student-visible results and denial for another teacher/course. A grade API receipt alone is not evidence of the complete classroom workflow.
7. Test the approved artifact policy: authenticated Margin link access/revocation; if ordinary Drive PDF delivery is later authorized, verify exact content, sharing, ownership and retention with explicit export intent.
8. For the later Add-on, test licensed and unlicensed users, admin installation/allowlisting, teacher discovery, student iframe launch, grading view, mobile behavior and published-app review requirements. Record actual sandbox and browser evidence separately from synthetic adapter tests.
