# Canvas integration: verified launch and enrollment foundation

The Canvas integration is **not complete or connected to an institution**. The current increment includes the protocol library in [`packages/lms`](../packages/lms/src/index.ts), an [HTTPS adapter](../apps/api/src/lms/http.ts) and a [PostgreSQL repository](../apps/api/src/lms/postgres.ts). It validates signed LTI 1.3 launches against a persisted installation and issues an installation/course-bound application session only for explicitly provisioned accounts and enrollments. The launch adapter itself provisions no student document and sends no submission, roster or grade request. A separate [assignment worker](ASSIGNMENTS.md) now implements tested durable backend student-document creation over a shared immutable inspected source; an optional [student content/operation adapter](ASSIGNMENT_WORK.md) now exposes current-launch manifests, permitted original PDFs and policy-aware annotation persistence. Browser routes now connect verified teacher selection to encrypted draft/create/return and verified student work to encrypted editing/synchronization. Default live-provider runtime and external services remain unconnected; actual browser evidence uses synthetic services and is recorded in [verification](VERIFICATION.md). Application startup still requires approved configuration and an authorized institution; locally composed fixtures are not a live Canvas connection. No Canvas account, developer key, deployment or external installation was created.

## Library behavior

`CanvasLMSProvider` implements the generic `LMSProvider` launch contract. Related types define installation-scoped user/course/assignment/submission/grade references so external IDs need not become application primary keys. Its advertised capability is only `lti-launch-verification`; unimplemented services do not return simulated success.

`beginLogin(installationId, input)` loads an enabled server-side registration. It checks initiation issuer/client/deployment and an exact registered target, then stores a five-minute launch attempt. State, nonce and the independent browser-binding secret have 256 bits of random input; the repository stores their digests. Opaque hints are forwarded without interpretation. The result contains the authorization URL plus a browser-binding value for a dedicated cookie.

`validateLaunch({state, id_token, browserBinding})` first checks the flow and browser binding. It verifies the JWT with RS256 and the registered platform key set, checks expected identity/time claims, and checks deployment/version/message/target/resource or deep-link settings. Untrusted additional audiences, substituted authorized parties, token-supplied key URLs, stale registrations and mismatched nonces fail closed. Registered trusted extra audiences require matching `azp`. Unknown unrelated claims are ignored; no name or email is retained in the normalized result.

The accepted token policy is deliberately bounded: 64 KiB token limit, five-minute maximum age, 30-second clock tolerance, maximum ten-minute issued-to-expiry interval, and issuance no earlier than 30 seconds before initiation. These are Margin policy choices, not claims that all possible platforms require exactly these values. Test them against an actual authorized Canvas launch before changing them. Errors expose no token content.

Platform key retrieval uses only the registered HTTPS URL, verified TLS and redirect denial. It enforces a five-second request/body deadline, 128 KiB decoded body limit, JSON/JWK-set content type and at most 64 keys. Each provider retains at most 128 key resolvers with least-recently-used eviction, a five-minute key freshness window and a 30-second refresh cooldown. Cache eviction, invalid/oversized responses and disabled TLS are tested; key-rotation interoperability still needs the actual platform.

Only successful validation atomically consumes state and reserves the installation-scoped nonce. The returned context is frozen. It includes the organization from the installation record, never an organization supplied in browser input, custom claims or external course ID. Role URIs become conservative hints, not application permission grants; unknown/shortened/lookalike roles do not grant a role.

Deep Linking opaque `data` preserves an empty string. Resource launches normalize only the signed `margin_assignment_id` custom field as a strict UUID; malformed values fail validation, and unrelated custom fields grant no application permissions. The optional `onVerifiedLaunch` server hook runs only after verification and committed session binding. Its redirect must exactly match a configured same-origin path without a query or fragment; arbitrary browser-provided redirects are rejected. The default has no assignment hook. The separate [assignment service](ASSIGNMENTS.md) implements encrypted authoring records and signed responses, with an optional authenticated HTTP adapter implemented but disabled by default; consuming UI and live institution wiring remain pending.

## Persistence and identity contracts

`InstallationRepository.findById` must resolve an administrator-provisioned installation with a stable `(issuer, clientId, deploymentId)`→organization mapping. Configuration changes must increment `version`; reassigning an installation's tenant or identifiers in place is unsafe. Recheck enabled state and grants when issuing an application session or performing a subsequent operation. Do not merge accounts by email: Canvas LTI subjects may differ from OIDC subjects and need explicit trusted account linking to an existing/invited organization membership.

`LaunchReplayRepository` is a required dependency; there is intentionally no production in-memory fallback. `PostgresLmsRepository` implements unique insertion, bounded reads and atomic all-field comparison/state consumption/nonce reservation under row locks. Nonce reservations last until token expiry plus clock tolerance. Repository restart and concurrent/repeated consumption are tested against actual PostgreSQL. A maintenance job still must purge expired rows; runtime has no broad receipt-delete grant. The earlier protocol-only Map fixture is explicitly synthetic.

The HTTP service uses the explicit `IdentityService.issueLmsSession` boundary; it never fabricates an OIDC callback. Enrollment resolution requires a live installation/version, an explicit subject-to-local-user link, a registered course, an enabled enrollment and an exact matching active organization membership. Only student/teacher/viewer are permitted; privileged roles require the independent MFA-capable identity path. No account is created or merged by email, launch role or custom claim. The pure launch library itself still issues no session.

## Browser binding and iframe boundary

The HTTPS adapter accepts bounded GET/POST initiation and a form POST response with duplicate/unknown-parameter rejection, a 96 KiB body limit, five-second body deadline, local admission/concurrency limits and no-store responses. It sets `browserBinding` in a five-minute `__Host-` Secure/HttpOnly/SameSite=None cookie and reads it independently from the response form. Per-flow cookie names support concurrent launches. The secret is never accepted from a form field, query string, localStorage or a value derived from state. Completion/error clears the matching flow cookie; launch tokens are not persisted or logged. Shared edge limits are still needed for multiple replicas.

The application BFF's ordinary SameSite=Lax login cookie is not a safe substitute: cross-site `form_post` has different delivery rules. If the binding is unavailable, fail and offer a top-level launch/restart. A cookie-blocked iframe is not grounds to skip state or nonce checks. Cookieless LTI Platform Storage requires its own standards-based origin/message validation and is not implemented by this package.

Current global frame denial remains intact. Only the short login continuation page may be framed by the enabled installation’s separately registered `frameOrigins`. That page contains an escaped, explicit user-gesture form targeting the top-level tab; it creates no launch cookie until initiation runs top-level. Launch responses themselves refuse iframe destinations. This is a top-level recovery path, not an embedded editor or an implementation of LTI Platform Storage. Browser-level interoperability in a real Canvas iframe remains unverified.

## HTTP and database composition

Apply [migration 001](../infra/migrations/001-identity.sql), then [migration 003](../infra/migrations/003-lms-installations.sql) as a migration owner. Migration 003 creates separate LMS runtime/provisioner roles and forced RLS for installations, launch attempts, nonce receipts, user links, courses, enrollments and session bindings. Runtime cannot create or change installations, identity links or enrollments. Installation identity tuples are immutable; changing approved configuration or enabled state must increment the version. Migration files do not seed accounts, courses or credentials.

`PostgresLmsRepository` requires certificate-verified PostgreSQL TLS and a separate 32-byte lookup HMAC key. A non-production test-only Unix socket exception supports the disposable fixture. It rejects globally disabled TLS, superusers, BYPASSRLS roles, inherited table ownership and identity runtime/provisioning or LMS provisioning roles. It requires durable `fsync`/`full_page_writes` settings and sets `synchronous_commit=on`. Parameterized queries use transaction-local RLS context, bounded pool/statement/lock timeouts and rollback cleanup. `lmsLookupDigest(key, 'subject'|'course', installationId, externalId)` creates installation-scoped pseudonymous mapping keys. Back up and manage that key independently; losing it breaks mappings. Deployment at-rest encryption remains an infrastructure requirement.

The composition root creates `LmsService` with the repository, an identity-issued `issueSession` callback and `authenticateSession`. Identity authentication injects `authorizeLmsSession: principal => repository.authorizeSession(principal)`. Session issuance is followed by a persisted LMS binding before cookies are returned. A failed binding leaves an unusable identity session; missing binding always denies later authentication. The binding rechecks current installation/version, explicit account link, course/enrollment, organization membership and live identity session on every authorization. Revocation does not rely on the original launch JWT staying valid.

| Route                                                      | Behavior                                                                                                                   |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `GET` or form `POST /api/lms/canvas/:installationId/login` | Registered launch initiation; iframe requests get the explicit top-level continuation                                      |
| `POST /api/lms/canvas/:installationId/launch`              | Bound Resource Link launch and approved existing enrollment/session                                                        |
| `POST /api/lms/canvas/:installationId/deep-link`           | Validates a Deep Linking request and enrollment; authoring response service exists separately, without HTTP/UI composition |
| `GET /api/lms/context`                                     | Reauthenticates and returns only provider, internal installation/course IDs, role and `launch-context` capability          |

`getSessionEnrollment(principal)` supplies the server-side current course scope. A valid session is not permission to access arbitrary organization documents. Generic document/upload/sync APIs must deny LTI sessions until a separately authorized assignment/resource-link-to-document mapping exists. The current success redirect enters the application without inventing an assignment. The API/runtime composition installs these handlers and denies generic LTI resource access; the combined HTTPS fixture verifies that restriction. Runtime is opt-in and still needs approved configuration before exposing an enabled installation.

Provisioning requires an institution administrator to approve the issuer/client/deployment→organization tuple, exact launch targets, service origins, separate frame origins, scope ceiling, existing local memberships and specific account/course/enrollment mappings. There is no public auto-enrollment endpoint or self-asserted linking flow. Future NRPS-based provisioning still needs a reviewed institutional policy and audit trail.

## AGS and NRPS boundary

`prepareServiceRequest(context, action)` produces a descriptor only. It accepts only this provider instance's frozen verified context, requires a still-current registration and token lifetime, and calls an injected application authorization check. Without that check every request is denied. Signed service URLs must use HTTPS without credentials/fragments and belong to the installation's explicit approved service origins. This is an SSRF boundary, not permission to follow redirects or arbitrary URLs in later responses.

| Action          | Scope requested                                                             | Descriptor                                                                                  |
| --------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Read roster     | `https://purl.imsglobal.org/spec/lti-nrps/scope/contextmembership.readonly` | GET supplied NRPS URL; requires context/version2.0 and installation grant                   |
| Write score     | `https://purl.imsglobal.org/spec/lti-ags/scope/score`                       | POST `/scores` under the signed line-item endpoint; preserves existing query                |
| Read line items | `https://purl.imsglobal.org/spec/lti-ags/scope/lineitem.readonly`           | GET signed line-items URL; uses broader `lineitem` only if that is the actual granted scope |

AGS scopes are intersected with the installation ceiling. The future service client still needs registered OAuth assertion signing, protected server token storage/caching, redirect denial and public/approved DNS egress policy, response schema/size validation, pagination allowlists, rate limits/backoff, integration revocation and auditable durable job authorization. A teacher-authorized job must not depend on a permanently retained launch token. Grade payloads/receipts, roster normalization and idempotent delivery are not implemented here.

## Durable student-work boundary

Migration 006 introduces a separate trusted provisioning worker with leased jobs and atomic private document/version/pages/key/grant/source-binding completion. Geometry must be authenticated to the exact inspected PDF version; legacy geometryless approvals are not eligible. The teacher PDF remains a shared immutable encrypted object, and students receive no generic grant on the teacher source. Current enrollment, pinned resource mapping, teacher ownership and source readiness are checked again under database locks before completion. Expired originating browser sessions can be retired independently of durable work provenance.

The worker has no Canvas HTTP client, scheduler, public route or automatic application composition. Assignment-origin documents remain blocked from generic OIDC/LTI sync. The optional [student work adapter](ASSIGNMENT_WORK.md) separately enforces current resource authority and supported tool/delivery policies. Its browser route is implemented; default live-provider composition remains disabled. [Immutable capture and internal annotation materialization](CANVAS_SUBMISSIONS_PLAN.md) are separately composed checkpoints; Author-only frozen review is now implemented. Canvas delivery, resubmissions, teacher feedback/grade return and live institution testing remain required work. Local PostgreSQL/synthetic-provider tests establish these backend boundaries only.
