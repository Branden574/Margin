# Canvas assignment authoring foundation

This increment provides a tested backend service, not a finished Canvas assignment workflow. [`AssignmentService`](../apps/api/src/assignments/service.ts) persists immutable assignment masters, captures verified Deep Linking selections, signs content responses and reserves private student work IDs. An optional authenticated HTTP adapter exposes the service to a configured application server; the default local entry point leaves it disabled, and a Canvas authoring/editor UI is not connected. No institution is connected, no live Canvas content response was sent and no hosted student editor is connected. A separately invoked, tested backend worker can now provision private student annotation documents from an authenticated shared source; it is not enabled in the local entry point.

## Current behavior

Every service operation resolves the current installation/course-bound LTI session. A teacher can create a master only from a document version they own and an approval returned by an injected authoritative ingestion/inspection service. A sync document row is insufficient. Missing inspection configuration returns `inspection_unconfigured`. The [ingestion registry and gateway](INGESTION.md) supply an independent readiness boundary, but real cloud storage, an isolated scanner and upload coordination are not configured in the default application; no scan approval is manufactured.

The immutable master contains a title, instructions, source document/version and encrypted artifact-version/scan-receipt snapshot. It also records an allowlist of annotation tools and explicit export, copy/paste, read-aloud and assessment choices. These policy values are validated and persisted; editor, sync, export and submission enforcement are not yet connected. An assignment record therefore must not be advertised as an enforced assessment.

The PostgreSQL repository uses a separate least-privilege runtime role, forced RLS and live checks of the identity session, installation version, explicit account link, course enrollment and organization membership. Teacher reads are restricted to their own masters. Student/viewer reads require a selected assignment bound to their current verified resource launch; sharing a course does not grant access to drafts or other selected assignments. Only the trusted launch-binding operation performs a narrow initial lookup for its verified assignment ID. It commits that read-only transaction, decrypts the selected master and verifies object availability outside any assignment transaction, then opens a fresh transaction that rechecks live course authority, the exact encrypted master fingerprint and the prepared database-only approval before committing the resource/session mapping. No unbound source is exposed through the browser API. Failed availability, revocation, changed master or mapping checks leave no resource/session binding.

Human-readable master metadata, source approval snapshots, policy and Deep Linking selection data use AES-256-GCM with separate wrapped data keys and entity/tenant-bound authenticated context. The request fingerprint used for idempotency is inside the encrypted payload, not a plaintext low-entropy hash column. Reusing a request ID with different content is rejected. Structural IDs, relationships, timestamps and state remain SQL columns and still require infrastructure encryption and restricted database access. Runtime credentials cannot rewrite a master or mark an inspection/source ready.

## Verified Deep Linking

The optional LMS `onVerifiedLaunch` hook runs after token validation and committed course/session binding. Only the normalized, verified launch is passed to the assignment service; browser JSON must never call this hook. The protocol parser preserves opaque Deep Linking `data`, including an empty string, and accepts only a validated UUID from the signed `margin_assignment_id` custom field. Unrelated custom fields grant no permissions.

A teacher Deep Linking request that accepts `ltiResourceLink` creates an encrypted, session-bound selection with a ten-minute expiry. Its return URL must have an approved installation service origin; its resource launch target must be the single registered Resource Link target. A selected master must belong to that teacher and course and still have an approved source. Completion signs an RS256 `LtiDeepLinkingResponse` with the tool client ID as issuer, the platform issuer as audience, deployment/version claims, a five-minute expiry and one resource item containing the opaque assignment UUID. It echoes platform data exactly. Cancellation produces an empty item list. No user identity, grade, score or due-date claim is fabricated.

[`AssignmentDeepLinkSigner`](../apps/api/src/assignments/deep-link.ts) accepts an independently managed RSA key and exposes its public JWK. It prepares an escaped HTTPS form POST using the `JWT` field, restricted form action, nonce-based CSP and no-store headers. The authenticated adapter now enforces current identity, LMS method, CSRF and origin checks before returning that document. A public-key/configuration endpoint, signing-key rotation service and consuming browser return flow remain unconnected.

Selection consumption is atomic and one-use. `selected_at` records a local signed selection, not confirmation that Canvas created or published an assignment. Delivery/response recovery is not implemented: a consumed selection requires a fresh Canvas launch after an uncertain return. The signed response omits a line item and uses Canvas's documented `preserveExistingAssignmentName` extension. Behavior still needs verification in an authorized Canvas test tenant.

The hook may return only an exact configured same-origin path. The service proposes `/canvas/author` or `/canvas/work`; these routes and their UI do not yet exist. The root LMS composition must add those exact paths to `launchReturnPaths` and configure the hook only when the consuming routes are ready. The current default hook remains absent, and generic document/upload/sync access remains denied for LTI sessions.

## Authenticated HTTP adapter

`createApi({ assignmentService, identityService, lmsService, ... })` enables the adapter only with both identity and LMS services. The local runtime does not configure it automatically. It accepts current LTI sessions only; an ordinary OIDC login, a development bearer token or browser-supplied role/course does not grant Canvas assignment access. Generic document, upload and sync routes remain denied to LTI sessions.

| Route                                           | Behavior                                                                                                                 |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/assignments/selection`                | Current teacher's session-bound selection or null                                                                        |
| `GET /api/assignments/current`                  | Current signed resource's title, instructions and policy; no source object/scan receipts                                 |
| `POST /api/assignments`                         | Create immutable master using the service's ownership, course and inspected-source checks                                |
| `POST /api/assignments/work`                    | Empty JSON object reserves the currently launched student's private work; HTTP 202 and `pending` do not mean provisioned |
| `POST /api/assignments/selections/:id/complete` | JSON `{assignmentId: UUID}` or explicit null cancellation returns the signed HTML form and restricted CSP                |

Every mutation requires the ordinary session-derived `X-CSRF-Token` and exact application origin. Authentication rechecks LMS federation before dispatch. Routes share the API's IP, tenant, user and concurrency limits. JSON has a 64 KiB limit and five-second input deadline; compressed bodies, invalid UTF-8, query overrides, unsupported methods and client-supplied work ownership are rejected. No HTTP route accepts a normalized launch or calls the trusted launch-capture hook from browser JSON. Request logs contain route templates, status and correlation identifiers, not titles, answers or response JWTs.

The return response is HTML, not proof of Canvas delivery. The consuming UI must arrange an authenticated, CSRF-protected top-level response flow before the launch hook can be enabled. Authoring screens, source selection, browser return recovery and live Canvas registration are still required. The existing service's fail-closed source gateway and pending student-copy boundary remain in force.

`tests/assignments.http.test.ts` exercises real HTTPS, ordinary identity and CSRF handling with synthetic in-memory identity and assignment repositories. Its ten cases cover revoked sessions/federation, origin/CSRF/role denial, bounded and stalled bodies, selection/cancellation response headers, private-source redaction and continued generic LTI denial. These adapter tests do not replace the actual PostgreSQL/RLS or signed-protocol suites. The PostgreSQL assignment suite also checks current-resource reads, absent launch, source revocation and enrollment revocation.

## Student work and provisioning boundary

A resource launch binds the installation-scoped HMAC of the Canvas resource ID to one selected assignment. It cannot remap an existing resource or reuse a session for a different assignment. A currently enrolled student can then reserve one private work record per assignment. Retries return the same work/document/version IDs. The work record and provisioning outbox row commit together; peer work is not readable through the student repository scope.

Migration [006](../infra/migrations/006-assignment-work.sql) and [`PostgresStudentWorkProvisioner`](../apps/api/src/assignments/provisioning/postgres.ts) implement **`pending` → `provisioned`** for the backend records. A completed record means the private document/version/pages/key/grant and encrypted source binding committed; it does not mean a browser editor, content route, Canvas submission or published assignment is available.

The reservation trigger pins the verified launch's registration version, subject/course digests and resource-link digest. It ignores caller-supplied provenance. The originating session UUID is an opaque audit identifier without a foreign key: retiring that session and its transient bindings does not revoke otherwise-current durable enrollment. The worker rechecks current student account/membership, installation version/enabled state, exact user/course links, enrollment, selected assignment and resource mapping. Existing pre-006 reservations without this provenance remain pending and unclaimable; no guessed backfill is performed. A reviewed reauthorization/migration operation is still needed for those rows.

`claimNext()` leases one due job with `FOR UPDATE SKIP LOCKED`, a random claim/token, increasing attempt and two-minute lease. At most ten attempts are allowed; retry delays are bounded to an hour, and exhausted/revoked jobs remain pending for operator attention. `prepare()` commits its initial read before decrypting the teacher master, authenticating scan-bound geometry and retrieving the exact encrypted object version through the injected storage reader. It checks the actual plaintext hash and clears bytes, then rechecks readiness. A receipt alone is never treated as object availability. Legacy scan approvals without authenticated page geometry fail closed.

Preparation produces an internal, process-local, one-use capability with a ten-second lifetime. It binds the current claim, encrypted assignment and source/scan/geometry state. New private page IDs, a unique annotation key and an encrypted completion/source-binding envelope are prepared before `completePrepared()` opens its transaction. The final transaction performs **no KMS, S3 or Canvas call**. It locks the relevant student/teacher authority, resource mapping and exact source records in a fixed order, rechecks them, and commits the student document/version/pages, student-only owner grant, wrapped annotation key, immutable encrypted receipt, work status and outbox completion together. A concurrent revocation either precedes the validation or waits until this transaction completes. Database locks do not guarantee that an S3 object will remain available later; every future content request must reauthorize and read its exact version.

The source PDF is shared immutably. There is **no S3 copy and no student grant on the teacher document**. Each student gets separate annotation identifiers and keys. The completion envelope authenticates the precise storage receipt, approved source/hash/scan, page geometry/IDs, assignment/student/target and claim. `receipt(claim)` recovers an uncertain commit by authenticating that encrypted envelope outside a transaction, then rechecking current authority, source state, actual target pages and the locked target document/student owner grant. Deleted targets or revoked owner grants cannot be reported as a recovered success. It does not infer success from an existing document row. Cancellation, stale claims, changed source state, malformed geometry or a failed final insert cannot leave a partial document.

The dedicated `margin_assignment_provisioner` login is never used in a request handler and cannot issue sessions, enroll students, change assignments, rewrite source metadata or read existing sync encryption keys. Its global reads are limited to encrypted masters/manifests, work/jobs and necessary identity/course/ownership columns. It can insert only its claimed student's target rows. PostgreSQL requires UPDATE permission to take `FOR SHARE` locks: narrow structural-column grants use a worker-only `USING(true) WITH CHECK(false)` policy, so even no-op changes are rejected. Mixed service-role and table-owner memberships, including SET-ROLE-only memberships, are rejected by service pool guards. No SECURITY DEFINER or RLS bypass is used.

Assignment-origin documents are denied by restrictive RLS in the generic sync route, including ordinary OIDC sessions with an owner grant. A future assignment content/sync adapter must enforce current course/resource membership and the assignment policy before exposing the shared PDF or edits. The current worker does not bypass that missing policy boundary. Teacher review grants, content/download routes, assignment autosave and policy enforcement remain unfinished.

The `AssignmentSourceGateway` contract is deliberately small:

- `resolveForTeacher(principal, {documentId, versionId})` returns an owned, scanned, encrypted, immutable artifact-version reference from authoritative ingestion or returns null.
- `stillAvailable(source)` rechecks scan revocation, version identity and object availability outside assignment transactions. A stored approval snapshot alone is not enough.
- `prepareAvailability(source)` performs authenticated object I/O outside the resource-binding transaction and returns a short-lived, one-use database-only recheck, or null. The ingestion implementation binds this check to the exact encrypted manifest/receipt/inspection state, expires it after ten seconds, and caps its database-only callback at one second. No KMS or object operation runs inside the final binding transaction.

The ingestion registry is implemented separately; real scan/storage integration, upload coordination and composition of the student-work worker are still required before exposing a complete authoring or student-editing workflow. Repeated full-object verification is deliberately conservative and has not been optimized or load-tested for 100,000 users. Teacher review access, assignment edits/versioning, co-teacher sharing, submission snapshots/receipts, resubmission, grading, roster synchronization, due dates and Canvas publication confirmation remain outside this increment.

## Database and verification

Apply migrations 001–004 for the assignment service; apply [005](../infra/migrations/005-ingestion.sql) and [006](../infra/migrations/006-assignment-work.sql) for authenticated geometry and durable student-work provisioning, using a migration owner. No source, assignment, account or enrollment is seeded. The assignment runtime login must have only the documented runtime role; it must not inherit identity, LMS or sync provisioning credentials. The repository requires verified PostgreSQL TLS, rejects disabled certificate verification, superuser/BYPASSRLS/ownership privileges and unsafe durability settings, and sets `synchronous_commit=on`. A test-only Unix socket exception is used by disposable fixtures. Retention, deletion, audit operations, backup/restore and maintenance roles still need deployment design and validation.

`tests/assignments.postgres.test.ts` uses an actual disposable PostgreSQL cluster and AES-GCM metadata encryption, generated RSA signing keys and cryptographic verification of the returned JWT. Its ready-source gateway is explicitly a synthetic test fixture, not a scan service. The 18 tests cover immutable encrypted masters, idempotency mismatch, ownership and policy validation, missing/quarantined sources, signed response/cancellation/replay, expiry/registration checks, private pending work/outbox creation, resource remapping, source/enrollment revocation, RLS role/course/peer isolation, author-only teacher reads, student/viewer draft and unlaunched-assignment denial, ciphertext tampering, TLS and credential safety, inherited and SET-ROLE-only owner escalation, a source verification delay longer than the database idle-transaction timeout, and revocation/assignment changes between preflight and final binding. The LMS protocol/HTTPS suites separately test the trusted hook and exact redirect allowlist.

Run `npm run build -w @margin/lms`, `npm run typecheck -w @margin/api`, and `MARGIN_REQUIRE_POSTGRES_TESTS=1 npx vitest run tests/lms.launch.test.ts tests/lms.http.postgres.test.ts tests/assignments.postgres.test.ts`. These checks prove local code/database behavior with synthetic identities and documents. They do not prove production durability, scanner correctness, real Canvas interoperability, browser iframe behavior or a completed end-to-end assignment workflow.

## Student-work verification

`MARGIN_REQUIRE_POSTGRES_TESTS=1 npx vitest run tests/assignment-work.postgres.test.ts` exercises actual disposable PostgreSQL with explicit synthetic storage/scanner fixtures. It covers transactional creation/recovery, encrypted source binding, independent student grants/page IDs, concurrent claims, stale leases/retry bounds, geometryless denial, missing/corrupt exact objects, cancellation, current authority and resource revocation, concurrent revocation serialization, completed-state immutability, partial-write rollback, peer/tenant isolation, generic OIDC denial, expired preparations, tampered geometry/receipt, legacy unpinned work, session retirement and credential separation. Lock-only grants are tested against real UPDATE attempts. These tests do not validate a malware engine, live AWS/Canvas, student editor behavior, production recovery or 100,000-user throughput.
